## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
As a developer operating a Prefab stream topology, I want to trace every message through the stream, so that I can find out which input messages contributed to any output message.

This is an **opt-in** feature: when not enabled, wire format and behaviour of existing streams are unchanged.

### Concepts
- **Message ID**: unique identifier of a single message, carried alongside the payload (as message metadata, e.g. a header, so payload schemas are unaffected).
- **Correlation IDs**: the message IDs of all messages that contributed to a newly generated message.

### Rules
1. A message ID is automatically assigned to every message published to a topic by a Prefab stream.
2. A message consumed from a topic that has no message ID is assigned a random one (not written back to the source topic; it is used as the message's identity within the stream and propagated to correlation IDs of derived messages).
3. A message that is derived from one or more other messages (map, flatMap, filter pass-through, join, aggregate, windowed aggregate, ...) gets correlation IDs referring to the message IDs of **all** contributing messages (e.g. a join references both sides; an aggregate references every message folded into the emitted result).
4. A message that does not originate from another message (e.g. published from outside a stream, or generated by a source/punctuator) has **no** correlation IDs; the metadata is absent rather than empty.
5. Existing message IDs on consumed messages are preserved, never overwritten.

### Scope / design questions to settle during analysis
- Opt-in switch: global property and/or per stream definition.
- Metadata representation per backend (Kafka: record headers; keep backend-neutral abstraction in the `streams` package, no Kafka types).
- Bounding correlation ID growth for long-running aggregates (cap/truncate policy).
- Access for user code (e.g. read current message ID/correlation IDs in operators) and for the topology test API from TASK-300 (`TopologySession` assertions on IDs).
- Documentation in the streams feature guide.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Tracing is disabled by default; with it disabled, no headers/metadata are added and existing behaviour and tests are unchanged.
- [ ] #2 With tracing enabled, every message published by a stream to a topic carries a message ID.
- [ ] #3 A consumed message without a message ID is assigned a random ID; a consumed message with an ID keeps it.
- [ ] #4 A message derived from one message carries that message's ID as its only correlation ID.
- [ ] #5 A message derived from multiple messages (join, aggregate) carries the IDs of all contributing messages as correlation IDs.
- [ ] #6 A message that does not originate from another message has no correlation IDs (absent, not empty).
- [ ] #7 The public streams API exposes no backend-specific types for message/correlation IDs; the Kafka backend implements them via record headers.
- [ ] #8 Behaviour is covered by backend-neutral topology contract tests for each operator type.
- [ ] #9 Streams documentation describes how to enable the feature and its semantics.
