## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
As a developer operating a Prefab stream topology, I want to trace every message through the stream, so that I can find out which input messages contributed to any output message.

This is an **opt-in** feature: when not enabled, wire format and behaviour of existing streams are unchanged.

### Concepts
- **Message ID**: unique identifier of a single message, carried alongside the payload (as message metadata, e.g. a header, so payload schemas are unaffected).
- **Correlation IDs**: the message IDs of all messages that contributed to a newly generated message.

### Rules
1. A message ID is automatically assigned to every message published to a topic by a Prefab stream.
2. A message consumed from a topic that has no message ID is assigned a random one (not written back to the source topic; it is used as the message's identity within the stream and propagated to correlation IDs of derived messages).
3. A message that is derived from one or more other messages (map, flatMap, filter pass-through, join, aggregate, windowed aggregate, ...) gets correlation IDs referring to the message IDs of **all** contributing messages (e.g. a join references both sides; an aggregate references every message folded into the emitted result).
4. A message that does not originate from another message (e.g. published from outside a stream, or generated by a source/punctuator) has **no** correlation IDs; the metadata is absent rather than empty.
5. Existing message IDs on consumed messages are preserved, never overwritten.

### Scope / design questions to settle during analysis
- Opt-in switch: global property and/or per stream definition.
- Metadata representation per backend (Kafka: record headers; keep backend-neutral abstraction in the `streams` package, no Kafka types).
- Bounding correlation ID growth for long-running aggregates (cap/truncate policy).
- Access for user code (e.g. read current message ID/correlation IDs in operators) and for the topology test API from TASK-300 (`TopologySession` assertions on IDs).
- Documentation in the streams feature guide.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
### Analysis (current state)
- `KafkaPrefabStream` is a thin wrapper over `KStream`. Value-only DSL operators (`filter`, `mapValues`, `flatMapValues`, `merge`, `repartition`) forward the input record headers unchanged. Joins, `aggregate` and `windowedAggregate` use `ValueJoiner`/`Aggregator`, which never see headers, and state stores persist the value only. Headers on join/aggregate output are therefore not reliable and no lineage can be accumulated across several input records.
- `StreamRecord` already has `Map<String,String> headers`; `KafkaRecords` and `KafkaPrefabProcessorContext` convert to/from Kafka headers, so custom `StreamProcessor`s can already read/write headers.
- `PrefabStreams`, `PrefabStream`, `StreamProcessor` and `StreamRecord` are backend-neutral and must stay free of Kafka types.
- `to(...)` serialises through `DynamicSerializer` with `Produced`; headers on the forwarded record are published as-is.

### Design
**Representation.** Two reserved record headers (constants in a neutral `be.appify.prefab.streams.tracing.MessageTracing`): `prefab-message-id` (random UUID string) and `prefab-correlation-ids` (comma-separated message IDs; header omitted when there are none). Payload schemas/Avro/JSON are untouched.

**Opt-in.** Global switch `prefab.streams.tracing.enabled` (default `false`) and `prefab.streams.tracing.max-correlation-ids` (default 100), carried as a `TracingConfig` record into `KafkaPrefabStreams`/`KafkaPrefabStream` (existing constructors keep delegating with tracing disabled). When disabled, the topology is built exactly as today (same nodes, same step names, same serdes). Per-stream opt-in is out of scope: lineage is only meaningful if applied to a whole topology.

**Key rule: IDs are minted only for messages that are persisted to a topic.** Chains of in-memory operators (`from → map → map → filter → to`) must not mint IDs on intermediate hops: those messages are never published, so a correlation pointing to them could never be resolved and the lineage would break. Instead, an in-flight record carries only its *origin set*: the IDs of the persisted (consumed) messages it derives from. The in-flight origin set is carried in `prefab-correlation-ids`; the `prefab-message-id` header is only meaningful on persisted messages.

**Semantics per operator:**

| Operator | In-flight origin set (`prefab-correlation-ids`) | Message ID |
|---|---|---|
| `from` (ingress) | `[ID of the consumed message]` (its existing ID, otherwise a random one, not written back to the source topic). Any correlation IDs already on the consumed message are dropped from the in-flight set: the consumed message itself is the parent. | the `prefab-message-id` header is removed from the in-flight record |
| `filter`, `branch`, `merge`, `repartition`, `deduplicate` | unchanged | none (in-flight) |
| `map`, `flatMap`, `keyBy`, `process` | unchanged: derived records inherit the origin set of their input, however many hops | none (in-flight); `process` may set an explicit origin set on the forwarded `StreamRecord`; forwarded from a punctuator with no input record, the set is empty |
| `join` | union of both sides' origin sets | none (in-flight) |
| `aggregate`, `windowedAggregate` | union of the origin sets of all folded-in records (capped), kept in the state store | none (in-flight) |
| `breakout` | lost (native `KStream`); records leave with an empty set | none |
| `to` | unchanged; if empty, the correlation header is omitted | **new random ID minted here**, for every message published |

Consequence: a message published to topic B whose input was consumed from topic A with ID `a1` carries `message-id=b1`, `correlation-ids=[a1]`; a downstream stream consuming B then correlates to `b1`. Every correlation ID therefore refers to a message that exists on a topic (except IDs randomly assigned to consumed messages that had none, which are by definition unresolvable and only stable within one processing attempt). Publishing the same unchanged record to a second topic mints a second ID, as each published message gets its own ID. Repartition topics only persist the in-flight origin set, no new IDs are minted there.

**Mechanics (Kafka backend, only when enabled).**
1. New package-private helper `KafkaMessageTracing` with two reusable `processValues` (`FixedKeyProcessor`) stages: `ingress` (move the consumed message's ID, or a random one, into the origin set) and `publish` (mint the message ID, before `to`). Because intermediate hops mint nothing, `map`/`flatMap`/`keyBy` need **no** tracing stage at all: header propagation of the existing DSL operators already carries the origin set. This keeps the enabled topology close to the disabled one (only an ingress and a publish node are added).
2. `flatMap` outputs all inherit the same origin set (they are the same parents). `keyBy` repartition topic carries the origin set header (headers survive the repartition topic; to be proven in the spike).
3. Joins and aggregations need the origin set inside the value because the DSL hides headers and state stores keep the value only. Introduce an internal `TracedValue<V>(V value, List<String> origins)` and a `TracedValueSerde` that wraps the existing `joinSerde` (length-prefixed origin list followed by the inner bytes). Before `join`/`groupBy` each side is wrapped into `TracedValue` from its header; the joiner/aggregator operates on the unwrapped value and merges origin sets (join: union of both; aggregate: running union kept in the state store, oldest evicted beyond the cap; windowed aggregate is naturally bounded per window). A final stage unwraps the result into value + origin-set header. `KafkaGroupedStream` is parameterised on the wrapped type internally; its public `PrefabGroupedStream` API is unchanged.
4. `KafkaPrefabStreamProcessorAdapter` remembers the origin set of the record being processed; `KafkaPrefabProcessorContext.forward` applies it to forwarded records, so chained and stateful processors keep lineage. An origin set set explicitly on the `StreamRecord` wins; punctuator forwards without one have none. Processors that buffer records and forward later can capture `StreamRecord.correlationIds()` and set it on the output.
5. Neutral API additions: `StreamRecord.messageId()` (`Optional<String>`), `StreamRecord.correlationIds()` (`List<String>`) and `withCorrelationIds(...)`, all derived from the reserved headers, so user processors can read and extend lineage without Kafka types.
6. Test API (TASK-300): `TopologyInput.send(value)` gains `.withMessageId(...)`; `TopologyOutput` gains `messages()` returning `OutputMessage<V>(value, Optional<String> messageId, List<String> correlationIds)`; `TopologyTestExtension.withTracing()` (or equivalent) enables the feature. Contract tests are backend-neutral, with Kafka-specific wire checks (header names, state serde) in `streams/.../kafka`.

### Risks and trade-offs
- Existing state and topics must keep working when tracing is switched on or off: see "Migration and compatibility" below.
- Extra serialisation/processor hop per operator; correlation lists add header bytes (bounded by the cap). Cap eviction means correlation of long-lived aggregates is best-effort; document it.
- `breakout` and global stores are outside lineage tracking.
- Spike first: confirm Kafka Streams (Spring Boot 4 / Kafka 4.x) keeps headers through `filter`, `merge`, `branch`, `repartition` and `TopologyTestDriver`.

### Migration and compatibility
Goal: switching tracing on (or back off) never breaks a running application or requires a state reset. Lineage that was never recorded is simply absent: legacy data reads as "no known origins".

**Where the format changes.** Only places where the origin set has to live inside the value because the DSL hides headers:
- window stores + changelog topics of `join`,
- key-value / window stores + changelog topics of `aggregate` / `windowedAggregate`,
- the internal repartition topic that `groupBy` inserts before the aggregation.

Everything else (`keyBy`/`repartition` topics, `to`, sources) is unchanged on the wire: the origin set rides in a record header and the payload bytes stay as they are. Other consumers of published topics only see two extra headers.

**Self-describing, tolerant envelope.** `TracedValueSerde` writes `0xFF 'P' 'T' <version>` + origin list + original payload bytes. Its deserializer detects the magic prefix: present → read origins and payload; absent → the bytes are legacy, return the value with an empty origin set. The prefix is unambiguous for Prefab payloads: JSON/String are UTF-8 (never starts with `0xFF`), Confluent Avro starts with `0x00`. The version byte leaves room to evolve the envelope.

**Tolerant reader is always installed, writer is opt-in.** The envelope-aware deserializer is used on the join/aggregate/groupBy serdes regardless of the tracing setting; the envelope is only *written* when tracing is enabled. Consequences:
- Upgrading Prefab with tracing still off: bytes written are identical to today, and the reader accepts them. Every instance is now "envelope aware".
- Enabling tracing (config change + restart, rolling bounce allowed because all instances already read both formats): stores and changelogs restore from legacy bytes, aggregates continue from the legacy aggregate with an empty origin set and then accumulate; entries are upgraded lazily on their next write. Repartition records still in flight from before the switch read as legacy.
- Disabling tracing again (rollback): new instances write legacy bytes and still read envelope bytes left in stores/topics, so rollback needs no reset either; origins in existing state are dropped as they are rewritten.
- Rolling-upgrade rule to document: first roll out the Prefab version that contains the tolerant reader (tracing off), then enable tracing in a second deployment. Enabling in the same rollout would let a not-yet-upgraded instance read envelope bytes it cannot parse.

**Topology identity.** Adding processor nodes can shift auto-generated node/store/topic names, which would orphan existing state. All current stores, repartition topics and join names are explicit (`Materialized.as`, `Repartitioned.withName`, `Grouped.with(name, ...)`, `StreamJoined.withName`), and every new tracing node (ingress, publish, wrap, unwrap) must be created with an explicit `Named` so it does not consume the generated-name counter. A test compares the set of state store names and internal topic names of representative topologies with tracing off vs. on (and against the pre-feature names) and must show them identical.

**Other compatibility notes.**
- Absent origin header on a record (e.g. produced by an older instance, or consumed from a repartition topic written before the switch) means "no origins"; it is never treated as an error and never mints an ID.
- Exactly-once and caching behave as before; the extra stages are stateless.
- Legacy join store entries are matched normally; the joined result simply lacks the lineage of the legacy side.

### Decisions (approved)
- Header names `prefab-message-id` and `prefab-correlation-ids`; correlation IDs are comma-separated in a single header so the encoding also works for systems without multi-value headers (Kafka itself supports repeated headers).
- Correlation ID cap defaults to 100 with oldest-first eviction.
- Message IDs are minted only when publishing (`to`); in-flight records carry origin sets.
- Opt-in is global only.
