## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Prevent internal-only reactor projects from being published to Maven Central and fail a release before creating/pushing release refs if its candidate bundle does not match the explicitly approved artifact manifest. Showcase variants and the benchmark must continue to compile and run in reactor CI. Release verification must inspect the release bundle generated by Central Publishing Maven Plugin without uploading or tagging.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The Central release bundle is inspected before the release commit/tag is pushed or any upload occurs.
- [ ] #2 An explicit manifest allows every intended public coordinate and payload/classifier, and rejects showcase/variant/benchmark coordinates, missing public coordinates, and unexpected classifiers.
- [ ] #3 Verification fails clearly for a missing/malformed bundle, duplicate entries, invalid coordinate paths or missing required signed/source/Javadoc artifacts.
- [ ] #4 The same verified bundle is the bundle uploaded for publication, or a deterministic equivalent is proven and guarded immediately before upload.
- [ ] #5 Tests cover a valid bundle, each rejection class, and fail-closed handling; internal projects remain part of the normal reactor build and CI.
- [ ] #6 Record findings and verification steps; preserve a documented recovery path for failed releases.
<!-- AC:END -->

## Implementation Plan
<!-- SECTION:PLAN:BEGIN -->
Inspect current Central plugin staging and the release script/workflow; reproduce plugin behavior in an isolated no-upload reactor. Add an exact artifact-manifest bundle validator and tests. Reorder release staging, validation, publication, and Git ref updates so no candidate is tagged or uploaded before validation and only the validated artifact is published. Keep examples and benchmark in the reactor for CI.
<!-- SECTION:PLAN:END -->

## Analysis
<!-- SECTION:ANALYSIS:BEGIN -->
- Showcase, showcase variant parent, all four variants, and benchmark already disable the injected Central publishing execution; benchmark additionally sets `maven.deploy.skip`.
- A no-upload probe using Central Publishing Maven Plugin 0.12.0 confirmed these seven artifacts are absent from the staged bundle even though they remain in the reactor.
- Previous releases do not include the current showcase or benchmark GAVs. Re-excluding them does not reduce the historical file count, but an allowlist is valuable to guard future POM/configuration regressions.
- Current `release.sh` tags and pushes before `mvn deploy`, so a bundle check must run before Git refs are created/pushed.
- Sonatype's `skipUpload` creates a bundle. Validate the exact candidate and determine a safe promotion path that uploads that same bundle; do not rely on an unchecked second build.
- The new Streams modules must publish sources and Javadoc like the existing libraries. The streams-engine test JAR is attached for sibling reactor tests, so its inclusion must be explicitly classified rather than silently ignored.
- The inherited GPG plugin can run before newly added per-module `verify` attachments; sources and Javadoc for the five new Streams modules must attach at `package`, before signing at `verify`.
- Central's upload API accepts one ZIP and the default `USER_MANAGED` mode validates it before manual publication. The release script validates before pushing refs and validates/reads the exact byte array again immediately before uploading it; uncertain upload outcomes require checking the portal before retrying.
- Standalone guard tests cover required and optional checksums, Windows ZIP paths, missing source/Javadoc/signature files, malformed manifests and archives, the explicitly allowed test classifier, and exact-byte upload against a local HTTP server. A mocked shell test verifies that guard failure precedes any Git ref creation or upload.
- A disposable signed release build exposed unsigned Streams source/Javadoc attachments with the earlier `verify` phase. A clean no-upload rebuild with the corrected `package` phase succeeded for all 29 reactor projects; the guard accepted its 516-file bundle, including signed sources and Javadoc for all five new Streams modules.
- Full Windows verification encountered the pre-existing agent-context path failure tracked in TASK-370. That test passed in an isolated Linux JDK.
- Full Linux reactor verification passed every module through AsyncAPI but failed in showcase integration tests because the registry repeatedly reset the connection while pulling `confluentinc/cp-schema-registry:8.4.0`. Later reactor modules were skipped. Rerun the complete suite once the image is available; this is not a guard failure.
<!-- SECTION:ANALYSIS:END -->
